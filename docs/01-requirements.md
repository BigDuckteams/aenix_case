# 01. Требования (разбор ТЗ)

Источник — презентация кейса «Java Blueprints» (AXENIX, 11 слайдов) и концепт интерфейса (слайд 4). Ниже требования кейса разложены на проверяемые пункты.

## 1. Цель

Нужно сделать веб-инструмент, который:

1. понимает Java-программу (монолит ≈1000 строк) и как **код**, и как **граф**;
2. **помогает её улучшить**: показывает дефекты и сложность, предлагает и применяет оптимизации, разбивает монолит на классы;
3. **доказывает**, что поведение сохранилось: после любого преобразования автоматические тесты подтверждают, что программа ведёт себя как раньше. Это ключевой контракт кейса.

## 2. Пользовательский путь (слайд 3)

```
01 Загрузить .java → 02 Разобрать код → 03 Построить граф → 04 Исследовать и править
                                                                  ↕ (синхронизация в обе стороны)
                          06 Запустить и сравнить ← 05 Собрать Java
```

- Изменения между кодом и графом синхронизируются **в обе стороны**.
- Шаг **06 «Запустить и сравнить» — обязательный финиш**: путь всегда заканчивается автоматической проверкой поведения.

## 3. Функциональные требования

Приоритет: **P0** — критический путь демо, **P1** — нужно для полного покрытия ТЗ. Оба уровня входят в MVP; приоритет задаёт только порядок работ.

| FR-03 | **Граф структуры**: классы, интерфейсы, record, enum, поля, методы; наследование, реализация, вызовы, использование типов | Для демо-монолита видны все типы и методы; клик по методу открывает его блок-схему | P0 |

| FR-09 | **Сборка Java**: компиляция текущей версии | Ошибки `javac` привязываются к строке и узлу; сборка кешируется по хешу содержимого | P0 |
| FR-10 | **Запуск**: stdin и аргументы, консоль stdout/stderr, код выхода, время | Кириллица корректна во вводе и выводе; таймаут и лимиты срабатывают; необработанное исключение показывается | P0 |
| FR-11 | **Сценарии**: ручные, импорт, автогенерация; покрытие узлов | Генератор на демо-монолите даёт покрытие узлов ≥ 80% за ≤ 60 с; покрытие видно на графе | P0 |

| FR-14 | **Оценка сложности Big O** для метода и фрагмента (любого узла) | Оценка видна на узлах-циклах и методах и объясняется цепочкой вкладов | P0 |

| FR-16 | **Оптимизация**: автоисправления с предусловиями, предпросмотр, применение через quality gate, пакетная кнопка «Оптимизировать» | На демо-монолите: сложность O(n²) → O(n) или O(n log n), все сценарии зелёные, ускорение измерено | P0 |

| FR-18 | **Выделение метода** (длинные методы, дублирование) | Выделенный фрагмент становится методом с правильными параметрами, возвратом и `throws`; клоны по желанию заменяются вызовом | P1 |
| FR-19 | **Экспорт**: текущая версия (`.java` / `.zip`), отчёт анализа и тестов | Скачанный архив компилируется `javac` без инструмента | P0 |
| FR-20 | **Трассировка** (кнопка «Дебаг»): запуск с подсчётом выполнений узлов, наложение на граф | Счётчики видны на узлах; непокрытые узлы отмечены | P1 |

## 4. Java scope

### 4.1 Обязательный (разделы 1–4, слайд 7)

| Раздел | Конструкции |
|---|---|
| 1. Язык и `java.lang` | пользовательские классы и интерфейсы; примитивы, обёртки, массивы; арифметика, логика, сравнение, приведение; `if/else`, `switch`, циклы, `break/continue/return`; методы, конструкторы, поля, `static`; `try/catch/finally` и `throw`; `Object`, `String`, `Math`, `System` и другие базовые классы |
| 2. Консольный ввод-вывод | `System.in`, `System.out`, `System.err`; `Scanner` и `Formatter`; `String.format` и `printf`; `StandardCharsets` для корректной работы с кириллицей |
| 3. Коллекции `java.util` | `Collection` и `Iterable`; `List`, `Set`, `Map`; `ArrayList`, `LinkedList`, `HashSet`, `TreeSet`, `HashMap`, `TreeMap`; `Iterator`, `Collections`, `Arrays`, `Comparator`, `Optional`; `List.of`, `Set.of`, `Map.of` |
| 4. Исключения | проверяемые и непроверяемые; `throws` и обязательный `catch`; собственные исключения через наследование; ключевые типы из `java.lang`, `java.util` и `java.io` |

### 4.2 Бонусный (слайд 8) — входит в MVP полностью

- `record` и `enum`
- дженерики
- лямбды и `java.util.function`
- Stream API и `Collectors`

### 4.3 Вне рамок (не делаем)

Многопоточность и `java.util.concurrent`, рефлексия, файловые операции и `java.nio.file`, сетевое взаимодействие, `java.time`.

Политика для кода вне рамок: инструмент **не ломается**. Такой код сохраняется как есть (блок «Код»), компилируется и запускается. Специальной поддержки в анализе нет, а недетерминированный вывод (например, текущее время) помечается в тестах как нестабильный.

Как каждая конструкция scope отражается в графе, правке, анализе и тестах — см. [04-code-graph-model.md § 9](04-code-graph-model.md#9-покрытие-java-scope).

## 5. Диагностика (слайд 5)

Для каждой находки пользователь видит:

- **строку кода и узел графа**;
- **объяснение** найденной проблемы;
- **оценку сложности** метода или фрагмента;
- **вариант исправления с ожидаемым эффектом**.

> «Диагноз должен быть проверяемым, а не только красивым» — для каждой находки есть доказательства: статические (цепочка причин) и динамические (счётчики, рост на масштабированных входах, сценарий-воспроизведение). Подробно — в [05-analysis.md § 10](05-analysis.md#10-проверяемость-диагноза).

## 6. Оптимизация и декомпозиция (слайд 6)

- Монолит `Main.java` (≈1000 строк: разбор, анализ, оптимизация, вывод) **при необходимости автоматически** раскладывается на классы по ответственностям (`Parser`, `Analyzer`, `Optimizer`, `Main`…).
- **Quality gate:** сборка + автоматические тесты = поведение сохранено.

## 7. Нефункциональные требования

| ID | Требование |
|---|---|
| NFR-01 | Производительность: разбор и граф для 1000 строк ≤ 300 мс; операция над графом ≤ 500 мс; анализ ≤ 1 с; quality gate на 15 сценариях ≤ 20 с |
| NFR-02 | Надёжность синхронизации: без правок код → граф → код возвращает текст байт в байт; форматирование и комментарии вне места правки сохраняются |
| NFR-03 | Детерминизм: одинаковый вход даёт одинаковые находки, сценарии (фиксированный seed) и план декомпозиции |
| NFR-04 | Безопасность запуска: таймауты, лимиты памяти и вывода, отдельный временный каталог, непривилегированный пользователь |
| NFR-05 | Кодировки: UTF-8 на всём пути; диапазоны для редактора — в UTF-16-колонках |
| NFR-06 | Воспроизводимость: `docker compose up` поднимает всё; зависимости зафиксированы lock-файлами |
| NFR-07 | Понятность UI: интерфейс на русском, тёмная тема по макету; статус «поведение проверено / не проверено» всегда виден |

## 10. Допущения

- Монолиты организаторов — валидный Java 17–21, компилируются `javac` без внешних библиотек, содержат одну точку входа `main`.
- Вход программы — только stdin и аргументы. Файлы, сеть, время и потоки не используются (вне рамок).
- **Поведение** = нормализованный stdout + нормализованный stderr + код выхода, а также тип и сообщение необработанного исключения.
- С проектом работает один пользователь (без совместного редактирования).
- `n` в Big O — обобщённый размер входа: размеры всех коллекций и входных данных считаются одним параметром.
