# 04. Модель кода и графа

Описывает, как Java-код превращается в граф, как операции над графом превращаются обратно в код, и как каждая конструкция Java scope отражается в блок-схеме.

## 1. Два графа

| Граф | Что показывает | Узлы | Рёбра |
|---|---|---|---|
| **Структуры** (`StructureGraph`) | Проект целиком: типы и их члены | Класс, интерфейс, record, enum; в них — поля, конструкторы, методы | `extends`, `implements`, `calls` (метод → метод), `uses` (метод → тип/поле), `contains` |
| **Блок-схема** (`FlowGraph`) | Один метод, конструктор или инициализатор | Блоки-операторы | Переходы управления: следующий, Да/Нет, тело цикла, выход, исключение |

Навигация по макету: дерево «Проект» слева → клик по методу открывает его блок-схему на холсте; на вкладке «Структура» — граф типов. Клик по блоку «Метод (внешний вызов)» открывает схему вызываемого метода.

## 2. Конвейер разбора

```
text (UTF-8) ──► tree-sitter CST ──► Semantic model ──► StructureGraph
                                                    └──► FlowGraph (на метод)
```

1. **CST.** tree-sitter возвращает узлы с `start_byte/end_byte` и `start_point/end_point`. Узлы типа `ERROR` и `is_missing` фиксируются как синтаксические ошибки.
2. **Семантическая модель** (`engine/java/semantic.py`):
   - таблица типов проекта (класс, интерфейс, record, enum, вложенные, анонимные, локальные) и их члены;
   - **области видимости** и объявления: локальные переменные, параметры, поля, лямбда-параметры, `catch`-параметры, переменные `for`;
   - **статический тип выражения** для простых случаев: литералы, объявленные типы переменных, поля, возвраты методов проекта, известные методы JDK (`String.length() → int`, `List.size() → int`, …);
   - **разрешение вызовов** методов проекта: по имени, числу аргументов и (при наличии) типам; при неоднозначности возвращаются все кандидаты;
   - **эффекты метода**: читает/пишет поля, читает stdin, пишет в stdout/stderr, бросает исключения, вызывает методы проекта (транзитивно). Используется анализом и декомпозицией;
   - **чистота** метода: нет записи в поля, нет ввода-вывода, нет вызовов нечистых методов.
3. **Граф** строится из CST и семантической модели детерминированно.

## 3. Структура графа блок-схемы

### 3.1 Типы блоков

Цвета и иконки соответствуют левой панели «Блоки» макета (Переменная, Условие, Цикл, Метод, Операция, Возврат) и расширены блоками, нужными для scope.

| Тип (`kind`) | Java | Видимый заголовок | Примечания |
|---|---|---|---|
| `method` | заголовок метода, конструктора, инициализатора | «Метод» | Корень схемы; в `data`: сигнатура, модификаторы, параметры, `throws`, дженерики |
| `var_decl` | `Тип имя = выражение;` | «Переменная» | `var` поддерживается; несколько деклараторов в одной строке — один блок |
| `assign` | `x = …`, `x += …`, `x++`, `a[i] = …`, `this.f = …` | «Присваивание» (в макете — «Операция») | Составные операции сохраняются как есть |
| `operation` | выражение-оператор: вызов, `new`, `System.out.println(…)` | «Операция» | Вывод `System.out/err.print*` получает бейдж «вывод» |
| `condition` | `if / else if / else` | «Условие» | Исходы `Да` и `Нет`; цепочка `else if` — вложенные условия |
| `switch` | `switch` (оператор и выражение), в том числе стрелочный синтаксис | «Выбор» | Дочерние блоки `case` (метки, `default`, guard-условия); `yield` для выражений |
| `loop_for` | `for (init; cond; update)` | «Цикл (for)» | Контейнер: тело внутри; `data`: init, cond, update |
| `loop_foreach` | `for (T x : coll)` | «Цикл (for each)» | Контейнер |
| `loop_while` | `while`, `do-while` | «Цикл (while)» / «Цикл (do-while)» | Контейнер; `do-while` помечается флагом |
| `try` | `try / catch / finally`, try-with-resources | «Try» | Контейнер с секциями `ресурсы`, `try`, `catch (Тип e)`, `finally`; рёбра исключений пунктиром |
| `throw` | `throw expr;` | «Исключение» | Терминатор ветки, ребро в ближайший подходящий `catch` или к выходу из метода |
| `return` | `return expr;` | «Возврат» | Терминатор ветки |
| `break` / `continue` | `break [метка]`, `continue [метка]` | «Прервать» / «Продолжить» | Ребро к выходу из цикла или к следующей итерации |
| `yield` | `yield expr;` | «Yield» | Только внутри switch-выражения |
| `call` | вызов метода проекта | «Метод (внешний вызов)» | **Накладывается** на `operation`/`var_decl`/`assign`: бейдж и пунктирное ребро в схему вызываемого метода. Не отдельный блок в потоке |
| `lambda` | лямбда / ссылка на метод | «Лямбда» | Вложенный контейнер с телом-выражением или блоком; рисуется внутри родительского блока как «карточка» |
| `local_type` | локальный класс, интерфейс, record, enum | «Локальный тип» | Раскрывается в отдельную схему структуры |
| `labeled` | `метка:` | «Метка» | Контейнер вокруг помеченного оператора |
| `sync` / `assert` | `synchronized` (вне рамок), `assert` | «Код» | Блок «Код» без структурной поддержки |
| `block` | `{ … }` | не показывается | Группировка; вложенные блоки раскрываются в их содержимое |
| `code` | всё, что не распознано | «Код» | **Запасной блок**: хранит исходный текст как есть; гарантирует, что ни одна строка не теряется |

### 3.2 Рёбра

| Тип | Значение | Оформление |
|---|---|---|
| `next` | Следующий оператор | Сплошная линия со стрелкой |
| `true` / `false` | Исходы условия (`Да` / `Нет`) | Зелёная / красная подпись |
| `case` | Из `switch` в `case` | Подпись с меткой |
| `body` | Из цикла в первое действие тела | Внутри контейнера |
| `back` | Возврат в заголовок цикла | Скрыто внутри контейнера, показывается пунктиром при выделении |
| `break` / `continue` | Выход из цикла / следующая итерация | Подпись |
| `exception` | В `catch` | Пунктир |
| `call` | К схеме вызываемого метода | Жёлтый пунктир (как «внешний вызов» в макете) |
| `return` | К выходу | Слабая линия |

### 3.3 Контейнеры

Циклы, `try`, `switch` и лямбды — **контейнеры**: их тело нарисовано внутри рамки (как цикл `for each` в макете). Раскладка ELK получает иерархию, поэтому рёбра не пересекают границы произвольным образом. Контейнер можно свернуть до заголовка с бейджем «N блоков».

### 3.4 Модель данных (Pydantic, фрагмент)

```python
class SourceRange(BaseModel):
    file: str
    start_line: int      # 1-based
    start_col: int       # UTF-16, 1-based
    end_line: int
    end_col: int

class FlowNode(BaseModel):
    id: str                       # стабильный структурный ID
    kind: NodeKind
    label: str                    # короткий заголовок: «Условие», «Цикл (for each)»
    code: str                     # краткий текст оператора (усечён для отображения)
    range: SourceRange            # весь оператор
    parent_id: str | None         # контейнер
    data: dict                    # поля по kind: условие, тип, имя, init/cond/update, case-метки…
    badges: list[Badge]           # вывод, вызов, исключение, defect:<finding_id>
    complexity: str | None        # «O(n²)» для циклов и вызовов (кеш анализа)
    errors: list[str]

class FlowEdge(BaseModel):
    id: str
    source: str
    target: str
    kind: EdgeKind
    label: str | None

class FlowGraph(BaseModel):
    method_id: str
    signature: str
    file: str
    nodes: list[FlowNode]
    edges: list[FlowEdge]
    entry: str
    exits: list[str]
    version_id: int
    content_hash: str
```

## 4. Структурный граф

- **Узлы:** `type` (kind: class/interface/record/enum, модификаторы, дженерики, `extends`/`implements`), `member` (field/ctor/method/initializer, сигнатура, диапазон, сложность и число находок для бейджей).
- **Рёбра:** `extends`, `implements`, `contains`, `calls` (метод → метод; вес — число вызовов), `uses` (метод → тип, метод → поле).
- Режимы показа: «Типы» (только типы и наследование), «Методы» (типы с методами и вызовами), «Зависимости» (кластеры для декомпозиции — см. [06](06-transformations.md)).
- Для монолита `Main` с 40 методами показывается граф вызовов с группировкой по кластерам.

## 5. Синхронизация код ↔ граф

### 5.1 Код → граф

Всегда полный пересчёт из текста: файл перепарсивается, граф перестраивается. Для 1000 строк это десятки миллисекунд, а потому инкрементальные обновления не нужны.

### 5.2 Граф → код: операции

Frontend отправляет **операции**, backend превращает их в `TextEdit(file, start_byte, end_byte, new_text)`.

| Операция | Параметры | Результат в тексте |
|---|---|---|
| `insert_node` | `parent_id`, `slot`, `index`, `kind`, `fields` | Вставка оператора, сгенерированного по шаблону типа, в нужное место с отступом |
| `update_node` | `node_id`, `fields` | Замена текста затронутой части оператора (условие, инициализатор, заголовок цикла…) без перегенерации остального |
| `delete_node` | `node_id` | Удаление оператора. Для контейнеров — вместе с телом (по подтверждению); `unwrap` оставляет тело на месте |
| `move_node` | `node_id`, `new_parent_id`, `slot`, `index` | Вырезать и вставить (с проверкой областей видимости переменных) |
| `duplicate_node` | `node_id` | Копия оператора рядом |
| `wrap_node` | `node_ids`, `wrapper` (`if`, `try`, `for`, `while`, `block`) | Оборачивает подряд идущие операторы |
| `unwrap_node` | `node_id` | Замена контейнера его телом |
| `add_branch` | `node_id`, `branch` (`else`, `else_if`, `catch`, `finally`, `case`, `default`) | Добавляет ветку к `if`, `try`, `switch` |
| `remove_branch` | `node_id`, `branch_id` | Удаляет ветку |
| `rename_symbol` | `symbol_id`, `new_name` | Переименование объявления и всех использований (по семантической модели, учитывая области видимости; затронутые файлы проекта) |
| `add_member` | `type_id`, `kind`, `fields` | Создаёт поле, метод, конструктор (по шаблону) |
| `update_member` | `member_id`, `fields` | Меняет заголовок: модификаторы, тип, имя, параметры, `throws` |
| `delete_member` | `member_id` | Удаляет член; предупреждает, если есть использования |
| `replace_code` | `node_id` или `range`, `text` | Прямая замена фрагмента текстом (блок «Код»; редактирование в инспекторе) |

Общий конвейер:

1. Найти узел по ID → его диапазон CST. Если ID устарел (версия ≠ HEAD), вернуть `409`.
2. Построить `TextEdit` по шаблону (раздел 5.4) или по спецификации операции.
3. Применить правки к тексту в одной «транзакции» (в порядке убывания смещений).
4. Перепарсить; если есть `ERROR`/`MISSING` — откатить, вернуть `422 INVALID_FRAGMENT` с сообщением и местом.
5. Создать версию; вернуть новый HEAD, список изменённых файлов, `focus_node_id` и граф затронутого метода.

Операции пакетные: массив операций применяется атомарно (используется перетаскиванием нескольких блоков, пакетными исправлениями, декомпозицией).

### 5.3 Идентификаторы узлов

ID — структурный путь, а не номер строки, поэтому он остаётся стабильным при вставке строк выше по файлу:

```
{file}#{TypePath}.{memberKey}/{path}
пример: Main.java#Main.processOrders(List<Order>)/for[0]/if[0]/else/call[1]
```

- `memberKey` — имя и типы параметров (как в сигнатуре).
- `path` — цепочка `kind[индекс среди однотипных соседей]`.
- ID пересчитывается на каждый разбор. После операции backend возвращает `id_map` для узлов, которых изменение коснулось, и `focus_node_id`; frontend хранит выделение по ID и переключает его по `id_map`.
- Если ID больше не существует (узел удалён или сместился) — выделение сбрасывается, но открытый метод остаётся.

### 5.4 Шаблоны генерации блоков

Блок из палитры (Переменная, Условие, Цикл, Метод, Операция, Возврат) вставляется по шаблону; пользователь потом правит поля в инспекторе.

| Блок | Поля формы | Результат |
|---|---|---|
| Переменная | тип, имя, значение | `int count = 0;` |
| Присваивание | цель, оператор (`=`, `+=`, …), значение | `total += price;` |
| Операция | выражение | `System.out.println("…");` |
| Условие | выражение; флаг «добавить else» | `if (cond) { }` + `else { }` |
| Цикл for | init, cond, update | `for (int i = 0; i < n; i++) { }` |
| Цикл for each | тип, имя, коллекция | `for (Order o : orders) { }` |
| Цикл while | условие; флаг do-while | `while (cond) { }` |
| Switch | выражение; метки | `switch (x) { case 1 -> …; default -> …; }` (по стилю файла) |
| Try/catch | тип и имя исключения; флаг finally | `try { } catch (Exception e) { }` |
| Throw | выражение | `throw new IllegalStateException("…");` |
| Возврат | выражение | `return result;` |
| Break/Continue | метка | `break;` |
| Метод | модификаторы, тип, имя, параметры, throws | заготовка метода |
| Вызов метода проекта | метод, аргументы | `processOrder(order);` |

Для полей формы работает валидация: выражение парсится отдельно как `expression`, тип — как `type`, имя — как идентификатор (и не должно конфликтовать с существующим в области видимости).

### 5.5 Правила форматирования

- Отступ определяется стилем файла (пробелы или табы, ширина — по первому вложенному оператору).
- Стиль скобок (`{` на той же строке) определяется по файлу; по умолчанию — K&R.
- Стиль `case` (двоеточие или стрелка) определяется по ближайшему `switch` в файле.
- Всё вне правки остаётся неизменным (NFR-02).

### 5.6 Round-trip гарантии

| Гарантия | Проверка |
|---|---|
| Без правок «код → граф → код» возвращает идентичный текст | Property-тест на корпусе: тождественный набор операций не меняет байты |
| Все исходные строки отражены в блоках (включая блок «Код») | Тест: объединение диапазонов блоков покрывает все операторы метода |
| После любой операции дерево без `ERROR` | Проверяется в каждой операции |
| Операция обратима | undo = переход HEAD на предыдущую версию |

Комментарии остаются в тексте. Комментарий непосредственно перед оператором отображается в подписи блока (второстепенно) и перемещается вместе с ним (`move_node`, `delete_node`).

## 6. Версии

- Каждая успешная операция, правка кода, автоисправление, декомпозиция создают `Version` с `parent_id`.
- Undo/redo — перемещение указателя HEAD по цепочке предков/потомков активной ветки. Новая операция после undo создаёт новую ветку (старая остаётся в истории).
- «Оригинал» — версия 1; сравнение «до/после» всегда доступно через diff-редактор Monaco.
- `meta` версии хранит список применённых операций и `symbol_moves` (из какого класса и метода в какой перенесены символы) — это нужно для декомпозиции и отчёта.

## 7. Диагностики и наложения на граф

Узел может нести **оверлеи**: бейдж находки (`defect`), сложность, покрытие (число выполнений из трассировки), ошибки компиляции. Они приходят отдельными запросами и накладываются на кешированный граф, чтобы не пересчитывать его.

## 8. Ограничения и поведение при нераспознанном коде

- Любой оператор, структуру которого мы не поддерживаем (`synchronized`, `assert`, меточные блоки в экзотических позициях), попадает в блок `code`: он виден, его можно перемещать и удалять, но нельзя править по полям (только текстом).
- Сложные выражения (вложенные лямбды, цепочки Stream) остаются **внутри** своего блока; вложенное тело лямбды показывается карточкой и открывается отдельной схемой.
- Анонимные классы показываются как блок «Локальный тип» внутри выражения.
- Лимит отображения: схемы больше 150 блоков раскладываются с автосвёртыванием контейнеров глубже 3-го уровня.

## 9. Покрытие Java scope

Колонки: **Граф** — как отображается; **Правка** — что можно менять на графе; **Анализ** — учитывается ли в оценке сложности и правилах; **Тест** — фикстура в `samples/scope/`.

### 9.1 Обязательный scope

#### Раздел 1 — язык и `java.lang`

| Конструкция | Граф | Правка | Анализ | Тест |
|---|---|---|---|---|
| Пользовательские классы | Узел типа; члены | Добавить/изменить/удалить член, переименовать | Метрики класса, связность | `scope/01-classes` |
| Интерфейсы (`default`/`static`/абстрактные методы) | Узел типа, ребро `implements` | То же | Вызовы через интерфейс считаются по всем реализациям | `scope/01-interfaces` |
| Наследование, `abstract`, `super`, `@Override`, полиморфизм | Рёбра `extends`; вызов через тип — к реализациям | Правка членов; переименование учитывает переопределения | Граф вызовов по иерархии | `scope/01-inheritance` |
| Вложенные, локальные и анонимные классы, `static`-вложенные | Вложенные узлы / блок «Локальный тип» | Правка тела | Учитываются как члены | `scope/01-nested` |
| Примитивы, обёртки, автобоксинг | Тип в блоке переменной | Правка типа | Правило `BOXING` | `scope/01-types` |
| Массивы (одно- и многомерные, инициализаторы) | Тип с `[]`, индексация в выражениях | Правка выражений | Стоимость цикла по массиву | `scope/01-arrays` |
| Арифметика, логика, сравнение, приведение, тернарный, битовые | Выражения внутри блоков | Правка выражения полем | Для оценки сложности выражения — O(1) | `scope/01-expr` |
| `if/else`, `switch` (оператор и выражение, `case ->`, `yield`) | `condition`, `switch` | Добавить ветку/`case`, править метки | Ветвление учитывается как `max` | `scope/01-control` |
| `for`, `for each`, `while`, `do-while`, метки | `loop_*` контейнеры | Править заголовок, тело | Основа Big O | `scope/01-loops` |
| `break`, `continue`, `return` | Терминаторы и рёбра | Вставка/удаление | Влияют на оценку цикла (раннее завершение) | `scope/01-jumps` |
| Методы: перегрузка, `static`, `varargs`, рекурсия | Узлы-члены; рёбра вызовов; рекурсия — самоссылка | Править заголовок, добавить метод | Рекуррентная оценка: линейная рекурсия, деление пополам | `scope/01-methods` |
| Конструкторы, `this(…)`/`super(…)`, блоки инициализации | Узлы-члены | Править | Входят в стоимость `new` | `scope/01-ctors` |
| Поля, `static`, `final`, константы | Узлы-члены; рёбра `uses` | `add_member`, `update_member` | Участвуют в кластеризации декомпозиции | `scope/01-fields` |
| `try/catch/finally`, multi-catch, `throw`, try-with-resources | `try`-контейнер с секциями | Добавить `catch`/`finally`, править типы | Исключения учитываются в потоке | `scope/01-try` |
| `Object` (`equals`, `hashCode`, `toString`), `String`, `StringBuilder`, `Math`, `System`, `Integer`/`Long`/`Double`/`Character`/`Boolean` | Вызовы внутри блоков | Правка выражений | Каталог стоимости JDK (раздел 3.2 в [05](05-analysis.md)) | `scope/01-lang` |

### 9.2 Бонусный scope (полностью в MVP)

| Конструкция | Граф | Правка | Анализ | Тест |
|---|---|---|---|---|
| `record` (компактный конструктор, методы, статические члены, вложенные) | Узел типа «record» с компонентами | Добавить/удалить компонент: обновляет заголовок, `new` не правит автоматически (предупреждение) | Метрики; `equals/hashCode` — O(1) по компонентам | `scope/b1-record` |
| `enum` (поля, конструкторы, методы, тела констант, `values()`, `valueOf`, `switch` по enum) | Узел типа «enum» с константами | Добавить/удалить константу | `switch` по enum — O(1) | `scope/b1-enum` |
| Дженерики (классы, методы, интерфейсы, ограниченные параметры, wildcard, diamond) | Параметры типа в заголовках и в блоках | Править параметры типа и аргументы | Тип-параметры сохраняются при выделении метода (выведение типов) | `scope/b2-generics` |
| Лямбды, `java.util.function` (`Function`, `Predicate`, `Supplier`, `Consumer`, `BiFunction`, `UnaryOperator`…), ссылки на методы | Блок «Лямбда» (карточка внутри блока) | Правка тела в инспекторе | Стоимость тела умножается на число вызовов потребителем (`forEach`, `map`, `removeIf`) | `scope/b3-lambda` |
| Stream API (`stream`, `filter`, `map`, `flatMap`, `sorted`, `distinct`, `limit`, `reduce`, `collect`, `count`, `anyMatch`, `mapToInt`, `IntStream.range`…) и `Collectors` (`toList`, `toSet`, `toMap`, `groupingBy`, `counting`, `joining`, `summingInt`, `partitioningBy`) | Цепочка показывается как **конвейер** внутри блока: этапы с типами | Правка отдельных этапов в инспекторе; добавить этап | Каждый этап добавляет стоимость (`filter` O(n), `sorted` O(n log n)); `distinct` O(n) | `scope/b4-stream` |

### 9.3 Вне рамок

Не поддерживается и не оценивается: потоки и `java.util.concurrent`, рефлексия, `java.nio.file` и файловые операции, сетевые API, `java.time`. Код с этими конструкциями сохраняется и компилируется, но анализ и правка ограничены блоком «Код».

### 9.4 Процесс сверки

1. Для каждой строки таблиц есть фикстура `samples/scope/<id>/Main.java` + сценарии.
2. Автотест `test_scope_matrix.py` на каждой фикстуре проверяет: разбор без ошибок, round-trip, граф без потерянных операторов, `javac` проходит, сценарии зелёные после тождественной операции.
3. Когда организаторы предоставят технический документ с полным перечнем конструкций — добавляем недостающие строки (открытый вопрос №1 из [01](01-requirements.md#11-открытые-вопросы-к-организаторам)).
