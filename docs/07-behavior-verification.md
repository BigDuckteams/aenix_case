# 07. Проверка поведения

Ключевой контракт кейса: **после любых преобразований автоматические тесты подтверждают, что поведение программы сохранилось.** Этот документ описывает исполнение Java, сценарии, эталоны, сравнение, трассировку, генерацию сценариев и бенчмарк.

## 1. Что такое «поведение»

Для сценария (stdin + аргументы) поведение — это кортеж:

| Компонент | Сравнивается |
|---|---|
| stdout (нормализованный) | да |
| stderr (нормализованный) | да |
| код выхода | да |
| необработанное исключение: тип и сообщение (стек-трейс — нет) | да |
| время выполнения | нет (только отчётность и бенчмарк) |

Внутренние детали — имена методов и классов, расположение кода — **не** являются поведением, поэтому декомпозиция не ломает тесты.

## 2. Исполнение Java

### 2.1 Рабочее пространство

Для версии создаётся каталог `builds/<content_hash>/`: `src/` — исходники из `source_file` (с сохранением путей/пакетов), `classes/` — результат компиляции. Если каталог уже есть (тот же хеш) — компиляция пропускается.

### 2.2 Компиляция

```
javac --release 21 -encoding UTF-8 -g -Xlint:all -d classes @sources.txt
```

- Вывод разбирается в диагностики `{file, line, column, severity, message}`; привязка к узлу — по диапазону.
- Таймаут компиляции — 30 с.

### 2.3 Запуск

```
java -Dfile.encoding=UTF-8 -Dstdout.encoding=UTF-8 -Dstderr.encoding=UTF-8 -Dsun.stdout.encoding=UTF-8 \
     -Duser.language=en -Duser.country=US -Duser.timezone=UTC \
     -Xmx256m -Xss1m -XX:+UseSerialGC -XX:TieredStopAtLevel=1 -Xshare:auto \
     -cp classes <MainClass> <args…>
```

| Параметр | Значение по умолчанию | Настраивается |
|---|---|---|
| Таймаут сценария | 10 с (до 60 с для бенчмарка) | да, на проект |
| Лимит stdout/stderr | 1 МБ каждый (обрезка + флаг `truncated`) | да |
| Память | `-Xmx256m` | да |
| Число параллельных JVM | число CPU (1–4) | да |
| Пользователь | непривилегированный `runner` | нет |
| Среда | пустая, `LANG=C.UTF-8`, `HOME=<tmp>` | нет |
| Рабочий каталог | пустой временный `tmp/run-<id>/` | нет |

- Stdin подаётся целиком из `scenario.stdin` (UTF-8) и закрывается (EOF).
- По таймауту убивается процесс и его потомки (Windows: `taskkill /T`, Linux: process group + `SIGKILL`).
- На Linux перед `exec` применяются `setrlimit` (`RLIMIT_CPU`, `RLIMIT_FSIZE`, `RLIMIT_NPROC`).
- Для `main`-класса в пакете используется полное имя (`com.example.Main`).

### 2.4 Результат запуска

```python
class RunResult(BaseModel):
    status: Literal["ok", "exception", "timeout", "output_limit", "compile_error", "internal"]
    stdout: str; stderr: str
    exit_code: int | None
    exception: ExceptionInfo | None     # {type, message, frames: [...]} разобрано из stderr
    duration_ms: int
    truncated: bool
```

Необработанное исключение определяется по stderr (`Exception in thread "main" <type>: <message>`) и коду выхода 1.

## 3. Сценарии

Сценарий — именованный набор входных данных программы.

| Поле | Описание |
|---|---|
| `name`, `description` | Название и описание |
| `stdin` | Текст ввода (UTF-8) |
| `args` | Аргументы командной строки |
| `source` | `manual` — создан руками; `imported` — загружен; `generated` — создан генератором; `scaled` — масштабируемый (бенчмарк) |
| `size_factor` | Для `scaled`: размер входа, на который он рассчитан |
| `enabled` | Участвует ли в gate |
| `stability` | `stable` / `masked` (с масками) / `nondeterministic` (исключён из gate с предупреждением) |

### 3.1 Источники сценариев

1. **Ручной ввод** в UI: имя, stdin, аргументы; запуск и просмотр вывода.
2. **Импорт:** `.json` (формат ниже), каталог `scenarios/` с парами `name.in` / `name.out` (если организаторы дадут ожидаемый вывод — он используется как эталон ожидания, см. 4.3), вставка текста.
3. **Автогенерация** (раздел 7).
4. **Из консоли:** кнопка «Сохранить как сценарий» после запуска с вводом.

Формат импорта:

```json
{
  "scenarios": [
    {"name": "empty", "stdin": "0\n", "args": [], "expected_stdout": "Заказов нет\n", "expected_exit_code": 0}
  ]
}
```

### 3.2 Нормализация

Применяется к stdout и stderr обеих сторон перед сравнением:

1. Окончания строк → `\n`.
2. Удаление хвостовых пробелов в строках (опция, по умолчанию выкл. — иначе меняется смысл форматированного вывода; включается автоматически для сценария с признаком `masked`).
3. Удаление пустых строк в конце вывода (опция, по умолчанию вкл.).
4. Маскирование нестабильных фрагментов по маскам сценария: регулярные выражения с заменой на токен (`\d+ мс` → `<MS>`, `@[0-9a-f]+` → `<HASH>`).
5. Из стека исключения сохраняются только тип и сообщение.

### 3.3 Нестабильные сценарии

Каждый сценарий **дважды запускается** при записи эталона. Если выводы различаются — сценарий помечается `nondeterministic`, а система предлагает автоматические маски для расхождений (числа, хеши, время). Если расхождение исчезает после маскирования — `masked`. Иначе сценарий исключается из gate с предупреждением (вне рамок: время, потоки, случайные числа).

## 4. Эталон и сравнение

### 4.1 Эталон

- При импорте создаётся версия 1 «Оригинал». Эталон (`baseline`) записывается прогоном каждого включённого сценария на **эталонной версии** (по умолчанию «Оригинал»; задаётся в `project.baseline_version_id`).
- Эталон хранит нормализованные stdout/stderr, код выхода, исключение, время и покрытие.
- Эталон нужно перезаписывать явно: после подтверждения FIX-* или по кнопке «Принять текущее поведение как эталон» (с записью в историю).

### 4.2 Сравнение

Для сценария `s` и версии `V`:

```
actual = run(V, s)
verdict = PASS    если normalize(actual) == baseline[s]
          FAIL    иначе (diff: stdout, stderr, exit, exception)
          ERROR   если V не компилируется или процесс не стартовал
          TIMEOUT если превышен лимит (при том что эталон укладывался)
```

Отчёт показывает: сводку `passed/total`, таблицу «Тест / Результат / Время» (как «Результат тестов» в макете: `testEmptyList`, `testSingleOrder`, `testLargeDataset`…), по клику на FAIL — построчный diff (Monaco DiffEditor или unified), сравнение времени с эталоном.

### 4.3 Если организаторы дали ожидаемый вывод

Для импортированных сценариев с `expected_stdout` проверяется ещё и `baseline == expected` при записи эталона. Расхождение — предупреждение «монолит не соответствует ожидаемому выводу» (это не ошибка инструмента).

## 5. Экспорт отчёта

Форматы: **JSON**, **Markdown**, **JUnit XML**. Содержимое: версия (хеш и описание), эталонная версия, список сценариев с вердиктами, времена, diff упавших, покрытие, ссылка на историю преобразований. Для комплекта сдачи (п. 03 «Проверка поведения») отчёт сохраняется в `reports/`.

Кроме того, сам инструмент можно проверить «снаружи»: `scripts/verify_samples.py` прогоняет корпус `samples/` через API и пишет сводный отчёт (используется в CI).

## 6. Трассировка и покрытие (`JbTrace`)

Для вкладки «Дебаг», доказательства находок и метрики покрытия.

### 6.1 Инструментирование

- Для каждого блока-оператора (`FlowNode`) и каждой ветки условия (`true/false`) выдаётся числовой ID. Таблица `id → node_id` сохраняется в `builds/<hash>-trace/nodes.json`.
- Исходный код **не меняется** в проекте: инструментированная копия генерируется только на время сборки.
- В начало каждого оператора вставляется `JbTrace.hit(id);`; в условия — обёртка `JbTrace.cond(id, expr)`, возвращающая значение условия и записывающая исход (для вычислений с побочными эффектами порядок вычислений сохраняется).
- Для выражений-лямбд и стрелочных `case` (без блока) тело оборачивается в блок.
- `JbTrace` — небольшой класс (`engine/runtime/java/JbTrace.java`): массив `long[]` счётчиков; по завершению (shutdown hook) записывает `hits.json` в `tmp/run-<id>/`.
- Лимит: 5 млн вызовов `hit` на сценарий — затем счётчики насыщаются (защита от замедления); флаг `saturated`.

### 6.2 Использование

| Задача | Как |
|---|---|
| Наложение на граф («Дебаг») | Выбрать сценарий → «Дебаг» → у каждого узла число выполнений, цвет по частоте, невыполненные — серым |
| Покрытие | `покрытие = выполненные узлы / все узлы` по набору сценариев; показывается в панели «Результат тестов» и в генераторе |
| Проверка диагноза | «Проверить» у находки PERF: прогон на размерах N, 2N, 4N, 8N → счётчики и время (раздел 8) |
| Поиск воспроизведения BUG | Генератор следит за покрытием узла и исключениями |

### 6.3 Ограничения

Инструментирование обрабатывает scope, указанный в [04 § 9](04-code-graph-model.md#9-покрытие-java-scope), а код вне scope оставляет неинструментированным. Результат трассировки — **оценочный**, не используется для вердикта «поведение сохранилось»; gate запускает **чистую** (неинструментированную) сборку.

## 7. Генерация сценариев

Цель: дать покрытие узлов графа без ручной работы и выявить расхождения после преобразований. Без LLM (ADR-03).

### 7.1 Источники информации

| Источник | Что извлекаем |
|---|---|
| Статический анализ ввода | Последовательность чтений: `Scanner.nextInt/nextDouble/nextLine/next/hasNext…`, `BufferedReader.readLine`, `args[i]`; структура: «первое число = n, потом n строк» (цикл чтения с границей из прочитанной переменной) |
| Условия | Константы из сравнений (`x > 100`, `"quit".equals(cmd)`, `case "add"`, метки `switch`, значения `enum`) — становятся граничными значениями |
| Формат-строки и парсинг | `Integer.parseInt`, `Double.parseDouble`, `split(",")` → типы и разделители |
| Исключения | Места, бросающие/ловящие исключения, → входы-провокаторы (нечисловая строка, пустой ввод, ноль) |

### 7.2 Вывод «схемы ввода»

Эвристика строит дерево:

```
InputSchema
├── Token(int, источник: nextInt@L12)         # n
├── Repeat(count=ref(n))
│   └── Line(Token(str), Token(int), Token(double))
└── Command-loop(while hasNext) с метками: add/remove/list/quit   # из switch
```

Если схему вывести не удалось, используется запасной путь (7.4).

### 7.3 Алгоритм (детерминированный, seed = hash(проект))

1. **Seed-набор:** пустой ввод; один элемент; несколько; граничные (0, 1, −1, `Integer.MAX_VALUE`, пустая строка, пробелы, кириллица, длинная строка); неверный формат для каждого токена.
2. **Мутации от констант:** значения из условий ±1; метки `switch`; слова-команды.
3. **Обратная связь по покрытию:** каждый кандидат запускается на трассируемой сборке; сохраняется, если покрывает новые узлы/ветки (greedy set-cover). Мутации: замена токена, вставка/удаление строки, повтор блока, изменение размера `n`.
4. **Бюджет:** до 200 запусков или 60 с или покрытие 100%.
5. **Минимизация:** итоговый набор сжимается (удаляются сценарии, не дающие нового покрытия); каждому даётся имя вида `gen_<тип>_<n>` с описанием («покрывает ветку `count == 0` в `processOrders`»).
6. **Проверка устойчивости:** каждый сценарий запускается дважды; нестабильные исключаются или маскируются.
7. **Эталон:** вывод оригинала записывается как baseline.

### 7.4 Запасной путь (без схемы)

Если ввод не распознан: набор «пустой ввод», «числа 0..N по строке», «слова», «большой текст», «случайные байты Latin/кириллицы» (по seed) + обратная связь по покрытию. Если программа не читает stdin вовсе (нет `System.in`) — один сценарий без ввода, и по каждому набору `args` — отдельный.

### 7.5 Результат

Набор из 5–25 сценариев, покрывающих ≥ 80% узлов демо-монолита, с отчётом: что покрыто, что нет (узлы, до которых не удалось добраться, показаны на графе серым — пользователь может добавить сценарий вручную).

## 8. Бенчмарк и эмпирическая сложность

Используется для «Ожидаемое ускорение», проверки находок и графика роста.

### 8.1 Масштабируемые сценарии (`scaled`)

- Если схема ввода найдена — генератор строит вход, управляемый параметром размера (`n` строк / `n` чисел / `n` элементов) с повторяемыми случайными данными (seed).
- Размеры: 1000, 2000, 4000, 8000 (по умолчанию, настраивается; для O(n²) на больших размерах — таймаут).
- Для проектов, где размер нельзя вывести, доступен ручной сценарий-шаблон с подстановкой `${N}`.

### 8.2 Измерение

1. Для версии и размера — 1 прогрев + 3 замера, медиана времени.
2. Параллельно (на трассировке) — счётчики выполнения целевых узлов.
3. Показатель роста `k` — наклон прямой в логарифмических координатах `log(time) ~ k·log(N)` (метод наименьших квадратов) по последним 3 размерам.
4. Вывод: `k ≈ 1.97 → ~O(n²)`, `k ≈ 1.05 → ~O(n)`, `k ≈ 1.15 → ~O(n log n)`.

### 8.3 Отчёт

График (shadcn Chart): время от размера для «До» и «После»; рядом таблица ускорений. Показывается в карточке находки (раздел «Проверить») и в итоговом отчёте оптимизации.

## 10. Контрольный список «доказательства» для демо

Для демонстрации сохранения поведения в финале ([12](12-demo-and-submission.md)):

1. Запустить «Оригинал» — вывод.
2. Применить оптимизацию или декомпозицию.
3. Запустить gate: сборка → N сценариев → зелёный отчёт «Поведение совпадает».
4. **Негативный контроль:** вручную внести ошибку в версию (изменить `+` на `-`) → gate краснеет, показывается diff. Этим демонстрируется, что проверка «ловит» изменения, а не просто всегда зелёная.
5. Экспортировать отчёт.
