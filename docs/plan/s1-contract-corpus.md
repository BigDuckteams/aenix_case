# S1. Контракт API и корпус примеров

**Часы:** H2–6 · **Треки:** A, B, C · **Веха:** M0

## Цель

1. Зафиксировать контракт между frontend и backend до реализации (contract-first), чтобы S3 и S4 шли параллельно.
2. Создать корпус Java-примеров: демо-монолит на ≈1000 строк и фикстуры scope. Без корпуса нечем проверять S2–S9.

## Зависимости

S0.2–S0.5 (скелеты и генерация типов).

## Артефакты

- `backend/app/schemas/*` и актуальный OpenAPI; `frontend/src/lib/api/schema.d.ts`; моки.
- `samples/` (демо, scope, монолиты, сломанные, вне рамок) + `scripts/verify_corpus.py`.

- [x] Фикстуры scope разделов 1–4 готовы; бонусные — тоже (первый проход).
- [x] `verify_corpus.py` зелёный (локально на JDK 17; на JDK 21 его запускает джоб `backend-jdk`, CI ещё не запускался).

Отклонения от плана:

- Сценарии лежат по одному файлу на сценарий, а не списком; формат — `ScenarioImportItem`, поэтому `samples/*/scenarios/*.json` можно импортировать как есть.
- README к фикстурам scope — одна таблица `samples/scope/README.md`, а не 38 файлов.
- Ошибки валидации запроса возвращаются как `400 BAD_REQUEST` (а не стандартный `422` FastAPI), чтобы все ошибки имели один формат.
- `pnpm gen:api` вызывает `openapi-typescript` с `--default-non-nullable false`: иначе поля запросов со значениями по умолчанию становятся обязательными в TS-типах.
- Локально не проверено на JDK 21 (на машине разработки только JDK 17): корпус написан без конструкций, которых нет в Java 17; `javac --release 21` проверит CI.
