# Корпус Java-примеров

Главный актив проверки инструмента ([docs/10 § 2](../docs/10-quality-and-testing.md)): на этих файлах проверяются разбор, граф, правка, анализ и преобразования. Каждый пример компилируется, даёт детерминированный вывод и сопровождается сценариями.

| Каталог | Назначение | Состояние |
|---|---|---|
| [`demo-orders/`](demo-orders/README.md) | демо-монолит ≈1000 строк: ввод команд, проверка, анализ, преобразования, вывод; 11 сценариев | готово (S1.3, S1.4) |
| [`analyzer-pairs/`](analyzer-pairs/README.md) | фрагмент слайда 5 кейса: вложенный перебор и `merge(a, b)`; 6 сценариев | готово (S1.5) |
| [`scope/`](scope/README.md) | минимальные программы по строкам таблицы [04 § 9](../docs/04-code-graph-model.md#9-покрытие-java-scope): разделы 1–4 и бонус, 38 фикстур | первый проход готов (S1.6), уточняется в S2 |
| [`out-of-scope/`](out-of-scope/README.md) | потоки, `java.time`, файлы, рефлексия, сеть | готово (S1.9) |
| [`broken/`](broken/README.md) | файлы с синтаксическими и семантическими ошибками | готово (S1.9) |
| [`monoliths/`](monoliths/README.md) | 4 дополнительных монолита 800–1100 строк: текст, склад, калькулятор выражений, граф дорог; по 9–10 сценариев | готово (S1.7), до 6 штук к H24 |
| `optimizations/`, `defects/` | пары «до/после» и примеры правил | появятся в S7–S8 |

## Формат

```
<пример>/
├── Main.java или несколько *.java   исходники (пакеты — подкаталогами)
├── scenarios/<имя>.json             сценарии, по одному на файл
├── expected_kinds.json              только scope/: виды блоков, которые обязаны появиться в блок-схемах
└── README.md                        что демонстрирует (кроме scope/ — там таблица в scope/README.md)
```

Сценарий — это элемент формата импорта (`ScenarioImportItem`, [07 § 3.1](../docs/07-behavior-verification.md)):

```json
{
  "name": "uncaught-exception",
  "description": "Необработанное исключение: команда boom, код выхода 1",
  "stdin": "add 1 Иванов Хлеб 2 45.5\nboom\n",
  "args": [],
  "expected_exit_code": 1,
  "expected_stdout": "…"
}
```

`name` совпадает с именем файла; `expected_exit_code` указывается, если он не 0; `expected_stdout` — нормализованный вывод (LF, без хвостовых пустых строк), записывается скриптом.

## Правила корпуса

- Только то, что входит в scope кейса. Потоки, `java.time`, файлы, сеть, рефлексия и источники недетерминизма (`nanoTime`, `Random()` без seed, `Math.random`) допустимы только в `out-of-scope/`.
- Вывод обязан быть определённым: не печатать итерацию по `HashMap`/`HashSet` от объектов с identity-хешем, а также `Set.of`/`Map.of` (порядок зависит от запуска JVM), не печатать тексты `NullPointerException` и стек-трейсы.
- Кодировка UTF-8, переводы строк LF (`.gitattributes`), кириллица в строках, комментариях и вводе — приветствуется.
- Не меньше трёх сценариев на пример (двух для `scope/`, восьми для `demo-orders`).

## Проверка

```bash
python scripts/verify_corpus.py                       # весь корпус: javac, два прогона каждого сценария
python scripts/verify_corpus.py demo-orders scope/01  # только выбранные примеры
python scripts/verify_corpus.py --update-golden       # перезаписать expected_stdout после осознанной правки
```

Нужен JDK 21+ (`javac` в `PATH`, `JB_JAVA_HOME` или `--java-home`); с более старым JDK скрипт собирает под его собственный `--release` и предупреждает. Структуру корпуса, разбор tree-sitter и наличие всех строк таблицы scope проверяет `backend/tests/unit/test_corpus_layout.py` (JDK не нужен).
